Before the first commit

This document is the specification and the review contract. It is not everything the work needs. What follows is the rest of the handover — short, and each line is something that stops the work if it is missing.

How to work

  • One pull request per work order, with the acceptance criteria copied in and answered line by line with evidence.
  • Never commit a secret, and never bypass the pre-commit hook. If it blocks you, it found something.
  • Schema changes go in the startup patcher in Program.cs — the SQLite list and the Postgres batch — so an existing database upgrades itself.
  • A migration that widens access is a defect. Backfilling a new column must never open something that was closed, and must never close something a customer already paid for. Say which, in the commit.
  • Report what you find. This codebase has produced a defect on nearly every feature touched. Finding one is the job working, not a distraction from it — write it down rather than fixing it silently inside an unrelated change.

How the plan changes

This document is versioned like code and is expected to be wrong somewhere. When it is: the finding goes back to the decision owner, the document is corrected, and the work follows the corrected document. The implementer is never caught between a specification and a reviewer — if the review contradicts the plan, the plan wins until it is changed.

What good looks like. Every figure this product shows can be traced to an entry, every entry balances exactly, every posting respects the period lock, and every screen belongs to exactly one company. A feature that satisfies those four is finished whether or not it is beautiful. A feature that does not is not finished however good it looks.

Where we stand

The product's own rule is that a module belongs here only if it posts to the general ledger. Measured against that rule today, two modules do not yet keep their side of the bargain — and one of them is on the hub already.

Inventory is on the hub but produces no COGS. Stock quantities move, the opname processes, and nothing reaches the ledger. Every gross margin the product reports is therefore revenue with no cost against it. This is the single largest correctness gap in the product and it sits inside a module users can already open.
The activity log is readable by anyone signed in, across every company. AuditLog has no CompanyId and /api/audit-logs checks only that you hold a token. Tested live with a Staff account: it returns other users’ emails, addresses and actions. Detail in Access & accountability.
PPN is modelled as a flat 11%, which is not the rate. Since PMK 131/2024 the rate is 12% against a DPP nilai lain of 11/12 for non-luxury goods. The money matches for ordinary sales; the faktur pajak does not, and luxury goods are under-collected outright. Detail in What decides adoption.
The Bank Indonesia rate was not from Bank Indonesia. The sync so labelled called a public aggregator and stored the result as an official BI rate, with an invented buy/sell spread. Corrected while writing this document — see Exchange rates — and worth naming, because nothing in the interface would ever have shown it.
Purchase bills post nothing either. A bill records a payable that the Statement of Financial Position never sees, and a PPN Masukan the Tax module counts from the document rather than from the ledger. The two sides of the Ekualisasi report cannot fully agree until this is fixed.

Rules that bind everything below

These are already enforced in the codebase. Every feature specified in this document inherits them; none of them is negotiable per module.

Double entry is exact

Sum(Dr) = Sum(Cr), compared with !=, never a tolerance. A run that would produce an unbalanced entry throws and posts nothing at all.

Money is decimal

float and double are banned end to end. Rounding is Bankers (MidpointRounding.ToEven) at two places.

Posted entries are immutable

Corrections go through void or reverse, never edit. The correction is part of the record; an audit that cannot see it is not an audit.

Period lock is honoured by every path

Any posting path — including automatic ones like depreciation — validates the transaction date before it writes.

Accounting logic lives on the server

The frontend never re-derives a balance. Two screens disagreeing about the same figure destroys trust in both.

The product records, it does not decide

Tax treatment, useful lives, deductibility: entered by the accountant, computed by the product. Guessing puts a position in someone's return that they did not take.

Working in this codebase

Read this before the first commit. Everything below was learned by getting it wrong here, in this repository, on this data. None of it is guessable from the type names, and most of it fails silently — which is the reason it is written down.

Traps that do not announce themselves

What you will assume What is actually true How it fails
JournalLine.AccountId is an account id It is a string holding the account code — "4-1000" — not the Guid. Joining on Account.Id matches nothing and every figure reads as zero. Cost one full rewrite of the PPN equalisation.
Header accounts hold no postings They do. 5-0000, 6-1000 and 6-2000 are flagged IsHeader and carry entries. Filtering !IsHeader silently dropped Rp 18.000.000 of expense from a fiscal reconciliation. Nothing errored.
SumAsync works on money The SQLite provider refuses a decimal SUM outright. Runtime exception in development only, so it reaches production untested. Read the rows and add them in C#, or branch on Database.IsSqlite().
Type == "Revenue" means sales It also catches OtherIncomeExpense — interest income, FX gains, gain on disposal. Peredaran usaha inflated against a DPP that never included it. Use AccountGroup == "Sales".
Query filters need a null guard They are fail-closed on purpose: e.CompanyId == CurrentCompanyId, with no !HasValue || escape. Re-adding the guard turns "no tenant context" into "every tenant's rows". Never restore it.
A bare fetch is fine Only apiClient attaches the bearer token, the X-Company-Id header and the idempotency key. Four calls in the onboarding wizard and company hook worked only because the endpoint was unauthenticated, and broke the moment it was not.
Framer Motion variants reach every child They propagate only through motion components. A plain <div> in between breaks the chain. Cards starting at opacity: 0 never animated in. The ones with whileHover appeared on hover; the one without never appeared at all and read as a missing feature.
A failed query lands in isError Only after retries stop. A query still retrying reports status: "pending". A 402 was retried, so a locked module rendered skeletons forever instead of the refusal. Use retryUnlessClientError from lib/query-retry.ts.
Content can start hidden and animate in It must not. If the animation does not run, the content is simply gone. Use CSS transitions for feedback, never JavaScript animation as the thing that makes content visible.
formatCurrency is safe for any figure It rounds to whole rupiah, which is right for IDR presentation and wrong for a balance check. A ledger out by cents printed two identical figures under a headline saying they disagree. Use formatModuleMoney.
new Date("2026-08-31") is that date It parses as UTC midnight and renders as the previous day west of Greenwich. Period lock and count dates drift by one. Split the ISO string by hand — see formatIsoDate.
Intl money output contains normal spaces It uses a non-breaking space between symbol and digits. String comparisons and test assertions fail for no visible reason.
Animated blur is cheap Animating scale on blur(120px) re-rasterises the layer every frame. Three of them ran forever on every dashboard page. Both ambient animations are now animation: none — leave them there.
Static export handles any hook useSearchParams needs a Suspense boundary or the route stops exporting. Build failure, late, with an unhelpful message.

Rules with no exceptions

  • Money is decimal. float and double are banned end to end, including in JavaScript totals. Round with MidpointRounding.ToEven.
  • Compare with !=, never a tolerance. A ledger out by 0,0001 is out. A tolerance was removed from this codebase deliberately; do not reintroduce one anywhere.
  • Build the entry, check it balances, then save. If debits do not equal credits, throw and post nothing. A partially posted run is worse than a failed one.
  • Every posting path calls IPeriodLockService.ValidateTransactionDate before it writes — automatic runs included.
  • Posted entries are immutable. Corrections go through void or reverse. Never add an edit path.
  • Accounting answers are computed on the server. The frontend renders them; it never re-derives a balance.
  • Every new tenant table gets a CompanyId and a fail-closed query filter in the same commit that creates it.
  • Schema changes go in the startup patcher in Program.cs — both the SQLite list and the Postgres batch — not only in a migration.

Frontend conventions

  • Monetary figures carry .font-money or sit in a <table>.
  • Depth is hairlines and tonal shifts. No shadows on in-flow cards.
  • Colour carries meaning: emerald posted or balanced, cyan the credit side, amber out of balance, red overdue or void. Never decorative.
  • Italic gradient headings need box-decoration-clone pr-[0.14em] pb-[0.08em], or every line but the last is clipped.
  • Module menus live in lib/module-nav.ts. A screen that is not in there cannot be reached from a sidebar.
  • Route groups (hub) and (workspace) do not appear in URLs. The hub has no sidebar by structure, not by condition.
Running it. start-dev.bat brings up the API on 5210 and the frontend on 3000. The development database is SQLite and is tracked in git, so a schema patch or a seed shows up as a change to balanceio.db — commit it deliberately or not at all. The API holds a lock on its own executable, so stop it before dotnet build or the build fails on a file copy.

The standards this is written against

SAK Indonesia was renumbered, effective 1 January 2024. The substance of each standard did not change; the numbers did, and a product that still says PSAK 46 is quoting a reference that no longer exists.

The rule is simple enough to check any row yourself: a standard that adopts an IAS takes 2 + the IAS number, one that adopts an IFRS takes 1 + the IFRS number. Standards with no international counterpart start at 3 and 4.

PSAK 109 requires an expected credit loss allowance on receivables, which this product does not yet produce at all.

Tax authority, separately

Accounting standards and tax rules do not move together, and the product must not pretend they do. Positions come from UU HPP and the regulations under it; rates change by PMK and KMK on their own schedule. Every rate belongs in a table with an effective date rather than in code — so a prior period can still be recomputed on the rules that actually applied to it.

Contacts — a shared master, not a module

Contacts posts nothing to the general ledger, so under the product's own rule it does not earn a door on the hub. It is not a small module; it is a different kind of thing — a master record every module reads.

It is configuration, and it lives where configuration lives: an icon in the hub navbar, an entry in the account menu, and a row under Settings. It appears in no module sidebar at all — repeating it four times would imply four lists, when the whole point is that there is one.

One party, several relationships

The model cannot express this today. ContactType is an exclusive enum — Customer, Vendor, Both — which already needed a special value to cover two roles and has nowhere to put a third.

Pihak A sells to you and buys from you. Both covers that. Pihak B is an employee who also invoices you as a consultant. Nothing covers that, and adding CustomerVendorEmployee to the enum is how an enum becomes a combinatorial mess.

Proposed change

Replace the exclusive type with independent role flags on the contact, each carrying the fields that role needs. Roles are additive and a contact may hold any combination.

Role Adds Used by
Customer Receivable account, credit limit, payment terms Sales invoices, aged receivables, PPN Keluaran
Vendor Payable account, payment terms, withholding profile Purchase bills, aged payables, PPN Masukan, PPh 23 / 26
Employee NIK, PTKP status, BPJS numbers, salary component set Payroll runs, PPh 21, BPJS reporting
Tax party NPWP, name on the tax document, PKP status Faktur pajak, bukti potong, Ekualisasi coverage

Migration The existing enum maps cleanly: Customer → customer flag, Vendor → vendor flag, Both → both flags. Nothing is lost and no contact needs re-entering.

Bank reconciliation — what it has to survive

This is the single biggest daily pain for anyone keeping books, and it fails on details rather than on concept. The specification is the list of things that break it:

  • Indonesian number format in imported files — 1.234.567,89, not 1,234,567.89.
  • Import de-duplication, so re-importing an overlapping statement does not double the ledger.
  • Timing differences: a cheque written on the 30th and cleared on the 3rd is not a discrepancy.
  • Bank-side sign convention, which is the mirror of the book side.
  • Transfer fees deducted by the bank and never recorded as an expense.
  • Statement continuity — a gap between one import's closing balance and the next one's opening.
  • Virtual account numbers buried in free-text descriptions, which is how a receipt is matched to a customer.

Where this module stops

BalanceIO is not a PJAP. It is not certified to issue tax documents and does not try to be, and that boundary is a design constraint rather than a gap to close later.

Not oursWhat we do instead
Issuing a faktur pajak Record the reference assigned in the DJP system against the invoice, and prepare the data for import there. The number is captured, never generated.
Allocating NSFP ranges Nothing. Ranges are requested and consumed in the DJP system.
Issuing bukti potong Record the withholding on the bill that created it, and prepare the data for e-Bupot.
Filing a return Reconcile the period so the figures being filed are defensible, and track the deadline. The filing is done by whoever holds that responsibility.
Deciding a tax treatment Apply what the accountant classified on the account or the counterparty. The judgement stays with the person who is answerable for it.
Vocabulary is a specification, not a style guide. Safe verbs: track, record, organise, reconcile, export, support. Unsafe: determine, calculate your tax, decide, issue, file for you. The distinction is the difference between a tool and a liability, and it is the reason the boundary above is written down rather than assumed.

Exchange rates

A company that transacts in foreign currency needs two different rates on the same day, for the same transaction, and they will not agree. Treating that as one number is the mistake. The gap between them is a real reconciling item, not an error to smooth over.

Rate Set by Cadence Used for
Kurs BI — JISDOR Bank Indonesia Daily, business days The spot rate for recognising and retranslating under PSAK 221. IDR/USD, built from interbank transactions through SISMONTAVAR.
Kurs BI — middle rate Bank Indonesia Daily The average of the buy and sell quote, for currencies other than USD.
Kurs Pajak — KMK Kementerian Keuangan Weekly, Wednesday to Tuesday Mandatory on tax documents: faktur pajak, PPN and PPnBM, bea masuk and bea keluar, and PPh on import and export. Set from the previous week average.
Contract rate The parties Per agreement Where a contract fixes a rate. Recorded as entered, never overwritten by a feed.
They are different numbers on the same day, and both are correct. A USD invoice recognised at the JISDOR rate and reported on a faktur pajak at the KMK rate produces two different rupiah figures for one sale. That difference is precisely what the PPN equalisation surfaces, and a product that quietly used one rate for both would hide it.

The sync labelled Bank Indonesia was calling a third-party aggregator and storing what came back as ExchangeRateSource.BankIndonesia, with a buy/sell spread of ±0.3% invented in code and shown as though a bank had quoted it. A rate decides a figure in the statements; if it is ever questioned, the answer has to be the rate actually used, from the source it actually came from. It is now recorded as an indicative market rate with no invented spread. Provenance is part of the number.

Rules the rate table has to hold

  • Never overwrite a rate a posted entry used. A retrieved rate corrects the table going forward; it does not rewrite history.
  • A missing rate is an error, not a zero. Posting into a date with no rate must refuse rather than value the transaction at nothing.
  • Store the source on every row — BI, KMK, market, manual, contract — and the KMK number where one applies.
  • Do not interpolate across a gap. A rate that was never published cannot be produced by averaging the days either side of it.
  • Published rates are global; the election is the company's. The same KMK applies to everyone. Which rate a company applies, and to what, is its own accounting policy and belongs in its settings.

What decides whether anyone actually switches

Everything above makes the product correct. None of it makes a company move five years of books into it. These four do — and the first one is a live defect rather than a missing feature.

PPN at twelve per cent

The rate in this product no longer exists in the regulation. Seven models default TaxRate to 11, and invoicing computes PPN = net × 11%. Under PMK 131/2024 the rate is 12%, and for non-luxury goods the base is a DPP nilai lain of 11/12 of the selling price — which is what makes the effective rate 11%.
CaseRateBaseEffective
Non-luxury goods and services12%DPP nilai lain = 11/12 × price11% of price
Luxury goods subject to PPnBM12%Full DPP12% of price
Export of goods0%Full DPPNil, but still reported
Besaran tertentuVariousPer the regulation for that sectorSet by PMK

For ordinary goods the money is unchanged, so nothing looks broken. Two things are:

  • The faktur pajak is wrong. It must state a 12% rate against the DPP nilai lain. A document showing 11% against the full price states a rate that is not in the law, and e-Faktur will not take it.
  • Luxury goods are under-collected by a full percentage point. There is no way to express “12% on the full DPP” in the model at all, so a company selling BKP mewah collects 11% and owes 12%. That is a liability, not a display bug.

What the model needs

ChangeWhy
A DPP scheme on every taxable lineStandard, nilai lain 11/12, besaran tertentu, or zero-rated. The rate alone cannot express the difference.
Rates in a table with an effective dateA rate change is then data entry, and a prior period can still be recomputed on the rules that applied to it — which is exactly what an amended return needs.
A PPnBM flag on the productIt decides both the DPP scheme and whether a second tax applies at all.
Rate and base printed on the documentThe faktur has to show what was applied, not just the result.

Cash flow projection

The first question an owner asks is not what the profit was. It is whether there will be enough money next month. The data is already in the system — receivable and payable due dates, recurring entries, the depreciation schedule — and nothing reads it forward.

  • Receivables by due date, weighted by how that customer has actually paid before rather than by when they promised.
  • Payables by due date, with the ones that carry a penalty for lateness marked.
  • Recurring entries and payroll, which are known in advance and are usually the largest line.
  • Tax deadlines with their amounts: PPN on the last day of the following month, PPh 21, PPh 25 instalments.
  • The point at which the balance goes negative, stated as a date rather than a chart to interpret.

This is the one report in the product that is about the future, which is precisely why it should say what it assumes on the same screen as the number.

Dimensions on the journal line

A company with two branches, three projects or four departments cannot run on a ledger with one axis. ProjectId exists on the journal entry — the header, not the line — which means a single entry cannot split a cost across two projects, and that is the ordinary case rather than the exception.

  • Dimensions on the line: project, department, branch, cost centre.
  • Defined per company, not fixed in code — the axes that matter differ by business.
  • Required or optional per account, so a cost account can insist on a cost centre while a bank account does not.
  • Every statement filterable by any dimension, which is what turns a ledger into management reporting.

Documents and evidence

File storage exists and is not attached to anything that posts. An auditor does not ask for the figure; they ask for the document behind it. The scan of the bill, the contract, the bukti potong, the bank slip — filed against the entry, visible from the entry, and exported with it.

Build the cost layerA movement table: date, product, quantity in or out, unit cost, and the running balance the method produces. This is the record COGS is read from — never the sales price.

Post the opnameDifference against an Inventory Variance account, not straight to COGS. A count difference is a control finding and should read as one.
Backfill or draw a lineExisting quantities have no cost history. Either import a cost basis or start the layer from a dated opening balance — and say which, in the note on the entry.

Done when

  • Selling a tracked item produces a balanced entry debiting COGS and crediting inventory.
  • The Statement of Profit or Loss shows a gross profit that is not equal to revenue.
  • Inventory on the Statement of Financial Position equals the sum of the cost layer, exactly.
  • Processing an opname with a difference posts to the variance account and moves the book quantity to the counted one.
  • An item with no inventory account is refused with a named reason, not posted somewhere convenient.
D3 · PPN at twelve per cent with DPP nilai lain Compliance · money on luxury goods Open

Seven models default TaxRate to 11 and invoicing computes net × 11%. Under PMK 131/2024 the rate is 12% against a DPP nilai lain of 11/12 for non-luxury goods. Ordinary sales come to the same money and a wrong document; luxury goods come to the wrong money.

File or conceptChange
New: TaxRate tableRate, DPP scheme, effective from, effective to. Every computation reads the rate that applied on the document date — which is what an amended return needs.
SalesInvoiceLine, PurchaseBillLineAdd the DPP scheme per line: Standard, NilaiLain11Over12, BesaranTertentu, ZeroRated.
Models/Product.csAdd a PPnBM flag. It decides both the DPP scheme and whether a second tax applies.
SalesInvoicesController.csCompute DPP from the scheme, then PPN from the rate on the DPP. Never rate × price directly.
Invoice documentPrint the rate, the DPP scheme and the DPP, not only the resulting PPN.

Done when

  • A non-luxury sale of Rp 1.000.000 shows rate 12%, DPP Rp 916.667, PPN Rp 110.000.
  • A luxury sale of Rp 1.000.000 shows rate 12%, DPP Rp 1.000.000, PPN Rp 120.000.
  • An invoice dated before the change still computes on the rate that applied then.
  • Existing invoices are untouched. A rate table correcting the future never rewrites a posted document.
D4 · Purchase bills post Correctness · unblocks the PPN input reconciliation Open

PurchaseBillsController contains no new JournalEntry. Payables and PPN Masukan never reach the statements. Mirror what SalesInvoicesController already does on issue.

Done when

  • Issuing a bill posts a balanced entry: inventory or expense, PPN Masukan, and the payable.
  • The line’s product decides whether it debits inventory or an expense.
  • Aged payables agrees with the payable account balance in the general ledger, to the rupiah.
  • Voiding a bill reverses the entry rather than deleting it.
  • The period lock refuses a bill dated inside a closed period.
D5 · Rotate the committed secrets Security · operational, not code Open

The JWT signing key and the SMTP password are in this repository’s history. The code already reads both from the environment and Production refuses to start on a burned key — but the values themselves are still exposed to anyone with a clone. No commit fixes this; only rotation does.

  • Generate a new signing key and set it in the production environment. Every existing session ends, which is the point.
  • Change the SMTP password at the provider.
  • Add the new key’s hash to the burned list only if it is ever committed — the list exists to prevent reuse, not to record rotations.

Definition of done, and how the work will be reviewed

This section is the contract. It is written before the work so it cannot be argued after it, and the review will use exactly these checks — not a different, stricter list invented on the day.

Every change, without exception

CheckWhat proves it
It buildsdotnet build with zero warnings introduced, npx tsc --noEmit clean, npm run build exporting every route it did before.
It was runThe endpoint called against the running API and the real response pasted into the pull request — not described. A screen loaded, not assumed to load.
It posts, and it balancesWhere the change writes to the ledger: the entry, its lines, and the ledger total before and after. Debits equal credits exactly.
It is scopedAny new table has CompanyId and a fail-closed filter. Any new endpoint has [Authorize] and a permission where one applies.
It honours the lockA posting path refuses a date inside a closed period, and the refusal is shown, not swallowed.
It reconcilesThe figure the feature produces ties to a statement. A number that agrees with nothing is not finished.
It survives both themesLight and dark, no raw hex, no shadow on an in-flow card, no horizontal overflow at 1280 and 1440.
It fails visiblyError and empty states are designed, not left to a spinner. Content never depends on an animation completing.

What the review will look for

Beyond the checklist, the review targets the specific ways this codebase has broken before. Expect these to be probed on every submission:

  • Tenancy. Two companies in the database, and every new list queried as both. A leak here outranks every other finding.
  • Silent drops. Header accounts, draft documents, void documents, uncategorised rows — anything a filter excludes gets counted and compared against the unfiltered total.
  • Decimal handling. Any float, any tolerance, any SumAsync over money, any rounding that is not Bankers.
  • Provenance. A stored figure that claims a source it does not have — the reason the Bank Indonesia rate was found to be an aggregator.
  • Claims in copy. A screen that says the product determined, calculated or filed something. Safe verbs: track, record, reconcile, organise, export.
  • Partial writes. A run that posts some rows and abandons others without saying which, or a loop of one HTTP request per record where one transaction belongs.
  • Half-states. Blocked items reported as complete — the depreciation screen once said every asset was charged while two could not be charged at all.
How to submit. One pull request per work order, with the acceptance criteria copied in and each line answered with evidence — a response body, a ledger total, a screenshot. “Tested locally” is not evidence. The review will reproduce anything it doubts, so an honest “not covered” costs less than a claim that does not hold.
What will not be treated as a finding. Style preferences, naming that follows the existing convention, and anything this document specified. If the plan is wrong, that is a plan defect and gets fixed here first — the implementer should not be caught between a document and a reviewer.
