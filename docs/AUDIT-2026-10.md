## C7 detail

Every migration after `InitialPostgres` was generated against SQLite (the model
snapshot carries `TEXT`/`INTEGER` types), so `dotnet ef migrations add` produced
nonsense diffs and schema changes moved into raw DDL in `Program.cs`, run at every
boot with its failure swallowed. That DDL covered only some changes. Booting the
previous code in Production mode against an empty PostgreSQL 16 database and
diffing the result against the model gave:

- 6 missing tables (the five above plus BudgetLines);
- 32 missing columns on existing tables, among them every segregation-of-duties and
  approval column (165 if the old boot patches had not run either: the migration chain
  alone also lacks 8 tables the patches created);
- 14 missing indexes and 12 missing foreign keys on existing tables, plus two FKs with
  the wrong delete rule (`FixedAssets` → category/location cascaded);
- three nullable columns the model declares NOT NULL.

Any query touching `JournalEntries` or `Companies` selects the missing columns, so on
such a database the ledger endpoints fail outright. This is the stronger form of C1.

What changed:

- `RealignSchemaWithModel` is idempotent (`IF NOT EXISTS`, guarded constraints,
  backfills) and brings a migrations-only database and one left by the old boot
  patches to the model. The snapshot is regenerated against Npgsql.
- `PostgresSchemaTests` build the model with `GenerateCreateScript()`, build a second
  database with `Migrate()`, and compare every column. They do it from a fresh
  database and from the old-boot-patches state (`LegacyBootPatches.sql`, a verbatim
  copy of the removed DDL). `MigrationDriftTests` fails when the model and snapshot
  differ.
- `Program.cs` no longer issues DDL. Production calls `MigrateAsync()` and a failure
  stops the process; other environments call `EnsureCreated()`. Reference rows (tax
  rates, `5-9000` variance account) are seeded by `ReferenceDataSeeder`.
- Removed: the `ALTER TABLE` auto-patch in the journal `GET`, `RepairController`, and
  the swallowed `try/catch` DDL in `force-schema-fix` (now one transaction,
  `IF EXISTS`).

**Before deploying:** back up. The migration attributes voucher rows that have no
`CompanyId` to their contact's company, or to the only company if there is one, and
otherwise aborts with an explicit message. Existing development `balanceio.db` files
must be deleted; `EnsureCreated` does not alter them and the SQLite patches are gone.

### T3 — Ledger versus report

Withholding is **not journaled** at bill or payment time. A bill credits Trade
Payables for the full total; payment vouchers settle that total; no PPh payable
account is touched. The withholding report is therefore computed from bills and
cannot reconcile with the GL, because the GL never holds the liability. The default
chart has no PPh 21/22/23/4(2) payable accounts (only `2-1400` "Income Tax Payable").

Proposed: add per-type payable accounts; at bill posting, credit the payable and
reduce Trade Payables by the withheld amount; build the report from those accounts.
Needs the answers to T1 first.

PPN settlement (*partly fixed*, A10): kurang bayar still credits `2-1400` (Income Tax
Payable) and lebih bayar debits `1-1450`, which the default chart does not have. Which
accounts should these be?

## Permission sweep

Every controller action now carries `[RequiresPermission]`, except sign-in and password
flows, the caller's own profile, permissions, notifications and files, the plan
catalogue, company profile read/status (the onboarding wizard runs for every role) and
the module-door list. `PermissionCoverageTests` fails on any new action outside that list.

Mapping: reads of ledger data `Finance.View`, reports and tax dashboards `Finance.Report`,
creates/edits/deletes `Finance.Create/Edit/Delete`, bank reconciliation matching
`Finance.Edit` and adjustments `Finance.Create`, exchange-rate changes `Finance.Edit`,
products and units `Inventory.View/Manage` (stock adjustment `Inventory.Opname`),
fixed-asset categories/locations `Assets.View/Manage`, invoice edit/void
`Sales.Edit/Delete`, diagnostics `Audit.View`, subscription reads `Settings.View` and
upgrade `Settings.Manage`. Subscription routes also reject a company id other than the
one in scope (any member could previously read, and request an upgrade for, any company).
Effect by role: Viewer is read-only; Staff keeps day-to-day work but cannot delete
accounts or change the subscription. The role-to-permission table itself is unchanged
and is the thing to review if a role should hold more or less.

## Role check of the UI

The built frontend was driven in a browser with one user per role (Owner, Manager,
Staff, Viewer) in one company, visiting all 102 dashboard routes, after the permission
sweep. Every route loads without a refused request for every role. The three settings
pages that need `Settings.View` (email settings, billing, billing history), which a
Viewer does not hold, show the no-permission panel to a Viewer instead of loading.

Found and fixed by the check:

- **Stock opname failed for every role** (500): `StockOpnameController` asked the
  container for the concrete `PeriodLockService`, which is registered only as
  `IPeriodLockService`. A test now builds every controller from the container.
- **The onboarding wizard trapped Staff and Viewers**: it opens for anyone while the
  company is not onboarded, cannot be dismissed, and its submit needs `Settings.Manage`.
  It now opens only for users who hold that permission.
- **A refused action said "restricted to Owner or Manager roles"** whatever the cause:
  the permission filter returned an empty 403. It now returns
  `{ code: "PERMISSION_DENIED", permission }` and the toast names the permission.
- **Every toast in the dashboard rendered twice**: the root and dashboard layouts both
  mounted a toaster.

Write controls are now gated by permission. `useCan()` and `RBACGuard`
(`components/auth/rbac-guard.tsx`) answer from the same permission list the API
enforces and fail closed until it has loaded; create-only pages show a
"Your role cannot do this" panel instead of a form the API would refuse. The journal
form doubles as the detail view, so for a role that cannot save it stays readable and
loses only its save and post buttons. Checked in the browser per role: Viewer sees no
write controls on the checked pages; Staff sees no Delete on accounts and no company
profile save; Owner and Manager see everything.

Pages with placeholder ids in the static export (`/documents/1`, `/purchases/orders/1`)
and module dashboards on an unentitled plan (402) behave the same for every role.

## Not done

- **Historical `AccountId` rows.** Detect with
  `SELECT count(*) FROM "JournalLines" l JOIN "Accounts" a ON l."AccountId" = a."Id"::text;`.
  A non-zero result means entries invisible to the reports; rewriting `AccountId` to
  the account Code is a one-line `UPDATE` but touches Posted lines, so it is left to
  the owner.
- **Lint.** 414 of the 451 remaining errors are `no-explicit-any`; 38 are React
  Compiler rules in animation components. CI reports lint without gating on it.
  Suggestion: demote `no-explicit-any` to a warning and ratchet.
- **Design-system items** (`.text-gradient`, shadows, raw hex): unchanged.
- CSV exports do not quote or escape fields (formula injection in a spreadsheet);
  `/api/health` returns the exception message; registering over an unverified account
  replaces its password. All low.
- The journal quota counts Drafts; `Audit:RetentionDays` can delete audit rows when
  set; the `ApprovalThresholdAmount` setting is stored and unused.
